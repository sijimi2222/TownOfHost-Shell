# Nova描画プールの最適化と開始時保護（ローカル開発版）

バージョン2.2.3を維持。実機未検証。公開・Steam配置は未実施。

## 変更

`Nova.cs` は、従来のマップ別固定プールを全量生成する方式から、照準用1体でTMPの文字メッシュを測り、表示名を組み立てて必要数だけ生成する方式へ変更した。
初期検査は1方向のみ、複数Nova間で同じFixedUpdate時刻に1回まで。8方向を初期検査する試作は模擬CPU・一時割り当ての増加があったため採用しなかった。

実際の発射角では、従来と同じ全線分の最終メッシュ・UTF-8サイズ・区間連続性を検証する。字体や方向によって初期プールが足りなければ、その検証済み計画に必要な数だけ追加する。追加は従来の共有1秒間隔キューを使い、元の上限を超えない。追加待機中は攻撃しない。30秒で準備できなければその発射を中断する。通常の準備済み発射ではチャージ・発射待ち・可視時間1.5秒を変更していない。例外的な追加準備では、可視化・攻撃の開始が遅れる場合がある。

使用後は再利用し、同一ラウンドで一度必要になったダミーを発射のたびに増減させない。会議・死亡・終了・破棄では所有者ごとに回収する。初期計画失敗時は照準を回収し、同じ失敗を毎フレーム再試行しない。

## 個数（照準を含む）

実数はホストのTMPメッシュ・字体・設定幅で決まる。次表は同じゲーム内フォント数値を使った参照モデルであり、実機の固定個数を約束するものではない。

|---|---:|---:|---:|---:|---:|---:|---:|
|The Skeld / MIRA HQ / Polusなど|10|3|70%|10|6|2|2|
|The Airship|15|4|73.3%|14|8|3|2|

旧10/11/15は生成目標ではなく、安全上限と従来の文字重なり密度を保つための容量として残す。別字体・細い幅では上限まで必要になる場合がある。太さを変えたり、線分を間引いたりして削減したものではない。

## 初回ロードの問題

`GameStates.Reset()` は `task=true` にする。旧Novaの `Phase` は `IsInTask` だけで初回生成を許しており、イントロ完了を要求していなかった。手元の最新BepInExログでも21:55:33.24の `NOVA_VISUAL_STATUS status=0 tiles=1` は、21:55:33.47のタスクフェイズ開始ログより前にある。初回生成がロード／イントロと重なり得る点はソースとログで確認した。

NovaのPhaseは `!Intro && AfterIntro` を必要とし、Airshipの初期生成は接続中の生存実プレイヤー全員の `PlayerState.HasSpawned` を待つ。死者・切断者・PlayerId254以上の描画ダミーは待たない。実プレイヤーのDataまたはスポーン状態が不明なら準備を進めない。全員の準備後に既存4秒の猶予を開始する。待機は `NOVA_STARTUP_WAIT` として1回記録する。

ただし、12人・Airship・Nova1人でホストが落ちた直接原因は未確定。最新ログにはOOM・Packet Spam・致命的な管理例外の記録がない。直前の別Playerログには標準HostInfoPanelの外見更新のNullReferenceがあるが、同一障害との関係は確認できない。確認したWindows障害記録に今回の開始時障害を特定する情報はなく、クラッシュダンプからの確定診断はできていない。生成時期の不備を修正したことと、クラッシュ解消の実証は区別する。

## 通信・メモリ

実CNOコードを合成Unity/通信で動かした12人・Nova1人・標準幅のモデルでは、Airship準備のSendOrDisconnect要求が60→16、10秒内ピークが43→16、キュー内最終送信時刻が14.12→3.34秒になった。これはイントロ／全員のスポーン待ち、4秒猶予、初期TMP検査を含まないキューだけのモデル時刻である。

同じ256BのSpawn・空名フレーム仮定を使う12人モデルの準備バイト数は15,690→4,184B。15人なら17,850→4,760B。実測UDP通信量ではなく、再送・通常同期・他役職などを含まない推定値。

比較した文字列の最大は参照ベンチで662B。全幅・向き・字体のテストで送信名800Bと1名12線分以内を検査した。元の文字・字体選択順・配置密度は維持し、変更前に取得した18条件の最終表示名と一致した。RPC番号・パケット形式・CNOのID割当処理は変更していない。標準的な仮定フレームで1000B以内でも、あらゆる外見情報・実通信でのサイズや切断耐性を保証するものではない。

常駐PlayerControl/描画物とその更新・生成通信は個数に応じて減る見込み。ただしUnityネイティブの実メモリは測定していない。模擬TMP（正規表現による代用品）の標準Airship準備の一時割り当ては約54KB→194KB、CPU約0.24→0.95msだった。初期メッシュ検査を追加した分であり、実ゲームのCPU/GC/RAM比較には使えない。総メモリ使用量が同じ割合で減ったとは判定しない。

## 維持した仕様と未確認事項

Airship70/他50、壁・扉貫通、旧 `-` 表記、幅・時間・防御・命中判定、星、複数人の独立性を維持。PetId例外対策・HUD HEADER_SPACE_V6は変更していない。公開ReleaseにController受付・生存ズーム等が入らない境界も維持する。

PC/Switch/iPhone/Androidでの実ピクセル、12人のロード安定性、実メモリ、回線・公式サーバーの制限、切断耐性は未確認。SDFの透明パディングなど既存の見え方の制約も残る。Airshipのスポーン完了印が更新されない特殊状況ではNovaを安全側で準備中に止めるため、GM・特殊モードを含む開始/再戦でも確認が必要。

次は非公開のテスト部屋で、まず1人のAirship→6人→12人（Nova1人）、最後に15人の順で開始・発射・会議・再戦を確認する。`NOVA_STARTUP_WAIT`→`NOVA_PREPARE_QUEUED tiles=... ceiling=15`→status=1、`NOVA_DRAW_PLAN`、NovaDistanceの描画/攻撃終点、Controllerの実測サイズを照合する。再発した場合は当該時刻のPlayer.log/LogOutput.logとクラッシュダンプを保存し、原因確定前に成功扱いしない。
